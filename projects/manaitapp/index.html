04 / ARCHITECTURE

共通化する。でも、無理に混ぜない。

ゲーム内の動作はCommonへ、Registry・Event・初期化などAPI差の大きい入口は各Loaderへ。添付の開発記録を、触れる経路図に整理しました。

common/forge/fabric/neoforge/buildSrc/
Common→共通interface→ServiceLoader→Forge実装

Forge固有の登録処理へ接続します。

ServiceLoader

Commonから実装クラスを直接参照せず、ローダーごとの処理を切り替えます。

CompatRegistry

共通側は「何を登録するか」を宣言し、登録方法はLoader側へ任せます。

CompatHolder

登録済みオブジェクトを、初期化順序に配慮しながらCommon側から参照します。

05 / LESSONS

3つに増やして、重複を減らす。

Registryのライフサイクル、イベント差、GUI通信、Gradle構成まで、マルチローダー化はアーキテクチャそのものへの挑戦でした。

イベントは名前の置き換えでは済まない
ForgeとFabricでは対応するイベントが一致しない場合があります。PlayerTickやノックバックなどは、同等の動作をどう作るかから検討しました。
GUIと通信は境界を整理する
MenuTypeやバッファの差を踏まえ、Commonへすべて押し込まず、ローダー固有の入口とデータ受け渡しを分離しました。全通信処理の共通化が完了した、という意味ではありません。
Gradleも設計の一部
Project with path ':common' could not be found といったエラーを通して、コードだけでなくモジュール階層とビルド構成の整合性も学びました。
現在も向き合う課題
イベント差、ネットワーク、DataGen、CapabilityとFabric Transfer APIの差、バージョン変更、Gradleの複雑さが継続的な設計テーマです。
